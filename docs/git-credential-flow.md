# Scoped Git Credential Flow

This document defines how Partners grants repository credentials to sandboxes for clone, branch push, and pull request creation.

## Goals

- Limit every credential to one repository whenever the provider supports it.
- Prefer short-lived credentials generated by the control plane.
- Separate clone, branch push, and pull request permissions.
- Prevent direct pushes to default branches by default.
- Keep raw secrets out of job results, logs, artifact manifests, and Task Weaver documents.

## Provider Choices

GitHub App installation tokens are the preferred GitHub integration path. GitHub documents that installation tokens can be restricted to selected repositories and narrower permissions, and they expire after one hour. GitHub personal access tokens should be a fallback; GitHub recommends fine-grained PATs over classic PATs where possible, and recommends GitHub Apps for organization or long-lived integrations.

GitLab project access tokens are acceptable for GitLab repositories when scoped to the project and minimal scopes. GitLab documents token expiration behavior and recommends using the most limited scope possible.

## Grant Model

The gateway stores a credential grant, not a raw secret:

```json
{
  "id": "gitcred_123",
  "provider": "github_app",
  "repository": {
    "host": "github.com",
    "owner": "example",
    "name": "repo",
    "defaultBranch": "main"
  },
  "operations": ["clone", "push_branch", "create_pr"],
  "allowedBranches": ["codex/*"],
  "expiresAt": "2026-07-05T08:00:00.000Z",
  "tokenRef": "secret://vault/gitcred_123"
}
```

The sandbox receives the secret only at execution time through an injected credential helper or short-lived environment secret. The job result and artifact manifest only reference the grant ID.

## Operation Rules

| Operation | Required scope | Default branch rule |
| --- | --- | --- |
| `clone` | repository read | Allowed for the target repository only. |
| `push_branch` | repository contents write | Allowed only to configured branch patterns such as `codex/*`. Direct default-branch push is denied unless explicitly enabled for a trusted automation lane. |
| `create_pr` | pull request API permission plus source branch | Source branch must satisfy the branch rule; target branch normally equals the repository default branch. |

The provider adapter must verify that the remote URL matches the grant repository before clone or push. If a job changes its remote to another repository, the gateway must deny push and PR creation.

## Sandbox Injection

Recommended HTTPS flow:

1. Control plane validates the grant and resolves `tokenRef` through the secret manager.
2. Provider adapter starts the sandbox with a temporary askpass helper or credential helper.
3. Helper returns credentials only for the approved host and repository path.
4. Adapter unsets credential helper configuration after clone/push.
5. Adapter redacts stdout, stderr, command arguments, remotes, and environment snapshots before writing logs.

SSH certificates or deploy keys may be added later, but they must follow the same grant model: one repository, short lifetime, branch policy, no secret material in durable results.

## Failure Handling

- Expired grants fail before the sandbox starts.
- Repository mismatch fails before injecting credentials.
- Unauthorized branch push fails before invoking `git push`.
- Any detected raw secret in logs is redacted before artifact creation.
- If publishing fails after a successful edit, the job still returns a patch artifact so external services can recover the change.
